<section class="ditana-section">
  <div class="ditana-section__eyebrow">Rolling release, without the risk</div>
  <h2 class="ditana-section__title">Every upgrade is reversible.</h2>
  <p class="ditana-section__lede">Arch's rolling-release model is a feature, not a bug — but it can land breakage on a Tuesday morning. Ditana takes the sting out by snapshotting the system before every upgrade, automatically.</p>

  <h3 class="ditana-stacked__title">Atomic snapshots, taken by a pacman hook.</h3>
  <Image src={installerSnapshots} alt="System maintenance dialog showing automatic system snapshots option enabled by default" class="ditana-stacked__image" />
  <div class="ditana-stacked__body">
    <p>On ZFS and BTRFS, snapshots are atomic and free — a few milliseconds before any package upgrade. On XFS and EXT4, Timeshift handles the same job via rsync, completing typical incremental snapshots in seconds.</p>
    <p>The first snapshot is created by the installer itself, just before the first reboot. That means you can roll back to a freshly-installed system from day one — no setup, no first-upgrade chicken-and-egg.</p>
    <p>System snapshots, not data snapshots: <code>/home</code> and other data volumes are never touched. Roll back the system; keep your work.</p>
    <p>For ZFS, Ditana ships its own <a href="https://github.com/acrion/zfs-autosnap">zfs-autosnap</a> fork that — unlike the upstream — removes the pacman lock file from the snapshot, so a rollback leaves you with a working pacman immediately.</p>
  </div>

  <p style="color: var(--sl-color-gray-3); font-size: 0.9375rem; margin-top: 1.5rem; padding-top: 1.5rem; border-top: 1px solid var(--sl-color-hairline-light);">
    <strong style="color: var(--sl-color-white); font-weight: 500;">Headless too.</strong> System hardening plus automatic snapshots make Ditana a viable Arch-based server choice — uncommon for a rolling release. The installer's <em>Server</em> profile skips the desktop install entirely and leans into the security defaults.
  </p>
</section>

<section class="ditana-section">
  <div class="ditana-section__eyebrow">Hardware-aware</div>
  <h2 class="ditana-section__title">It checks the upstream sources at install time.</h2>

  <div class="ditana-showcase">
    <Image src={installerNvidia} alt="NVIDIA driver decision dialog with detected PCI ID and recommendation rationale" />
    <div class="ditana-showcase__body">
      <h3>NVIDIA detection, four-way decision.</h3>
      <p>Ditana queries the live PCI ID lists from <code>github.com/NVIDIA/open-gpu-kernel-modules</code> and the official legacy GPU page at install time. Based on the result, it recommends one of four driver options – nvidia-open-dkms, the legacy proprietary <code>nvidia-580xx-dkms</code>, the older <code>nvidia-470xx-dkms</code>, or nouveau – and checks that the package it is about to recommend is present in the repository, reverting to nouveau when it is not.</p>
      <p>It then explains what it picked, and why.</p>
    </div>
  </div>
</section>

<section class="ditana-section">
  <div class="ditana-showcase">
    <div class="ditana-showcase__body">
      <h3>CPU vulnerabilities, detected and mitigated.</h3>
      <p>Spectre v2, Meltdown, MDS, TAA, MMIO Stale Data, RETBleed, SRSO, GDS, RFDS — Ditana reads <code>/sys/devices/system/cpu/vulnerabilities/</code> at install time, <a href="/under-the-hood/mitigations/">enables only the mitigations your CPU actually needs</a>, and lets you review each one with documentation.</p>
      <p>Every mitigation comes with its <em>cost</em> spelled out, so you can make an informed call instead of choosing between "secure default" and "fast default" blindly.</p>
    </div>
    <Image src={installerMitigations} alt="CPU vulnerability mitigation dialog showing detected vulnerabilities and selectable mitigations" />
  </div>
</section>

<section class="ditana-section">

    <div class="ditana-showcase__body">
      <h3>System hardening, opt-out by default.</h3>
      <p>Unprivileged user namespaces restricted to the programs that need them. Restricted ptrace. Hidden kernel pointers. Hardened FIFO and regular-file protection in sticky directories. SYN cookies, no ICMP redirects, no source routing, reverse-path filtering. Each option ships enabled, each one is explained – and developers get a profile that loosens the right things for debugging.</p>

<section class="ditana-section">

  <h2 class="ditana-section__title">The installer is small. The knowledge base is big.</h2>
  <p class="ditana-section__lede">A Linux installer should do more than partition, install packages, and hand off. PKGBUILDs only know about their own package — they can't know what else is on the system. Ditana keeps the cross-cutting decisions in a separate, auditable knowledge base.</p>

  <div class="ditana-showcase">
    <div class="ditana-showcase__body">

Nobody would consider requesting that, and nobody needs to: the rule stands beside the package list, where a reviewer can see both the condition and the reason for it, rather than being hidden within installer code.</p>
